**Default for AI-statistician product**: ship **3-agent**. It's the sweet spot — meaningful improvement over 2-agent for cheap, while 4-agent's extra cost only pays off when Lean formalization rigor is a hard requirement (academic publishing, FDA submission).

### Empirical surprises

**1. 4-agent's Lean retry actually worked in this run.** For Bernoulli round 1, 3-agent's Lean stmt was `✗ ill-typed (continuing anyway)`. 4-agent retried and got `✓ type-checks (attempt 1)`. So the FormalVerifier sub-loop has measurable impact — but it didn't translate to better *convergence* because the failure was on the math side, not Lean.

**2. 4-agent doubled the cost but didn't double the win-rate.** Going from 3 → 4 agents: tokens +66% (6,897 → 11,453), cost +51% ($0.0198 → $0.0300), wall-clock +65% (29.8s → 49.1s). **All for the same 1/2 convergence**. Diminishing returns kick in fast.

**3. Token cost grew super-linearly with agent count.**
- 2 → 3: +20% tokens (+1 LLM call/round, but smaller per call)
- 3 → 4: +66% tokens (+1-2 LLM calls/round AND more context repetition)

Each split adds "translation overhead" — each agent has to re-explain context to the next. After 3-4 agents you start fighting yourself.

### The "diminishing returns" model

Let `n` = number of agents, `q` = quality of each agent's output (1.0 = perfect).

- **2 agents**: quality = q² (one big-context multi-task LLM call)
- **3 agents**: quality = q × q^(0.9) × 1.0 (specialized prompts, but +1 translation hop)
- **4 agents**: quality = q × q^(0.95) × q^(0.85) × 1.0 (more specialization, more translation loss)

For Claude Haiku 4.5 with q ≈ 0.85, optimal n in our experiments is **3**. With a stronger model (Opus, q ≈ 0.95), 4-agent might start winning. With a weaker model, 2-agent's simpler architecture might win.

**Lesson for production**: tune agent count to model quality.

## When to use which (decision tree)

```
Is Lean formalization a hard requirement?
├── YES (publishing to Mathlib, FDA submission)
│   └─ 4-agent ★ (FormalVerifier retry on Lean type-fail)
│
└── NO (just need verified estimator + simulation)
    │
    Do you have multiple LLM tiers (Opus + Haiku + small)?
    ├── YES → 4-agent (max per-role model choice)
    │
    └── NO (single model throughout)
        │
        Is cost the dominant constraint?
        ├── YES → 2-agent (cheapest per query, accept higher failure rate)
        │
        └── NO → 3-agent ★ (sweet spot for production)
```

## Caveats (the honest version, again)

- **N = 2 questions × 1 seed × 1 LLM**. A proper study needs ≥ 20 questions × 5 seeds × 3 models. These numbers are *suggestive*, not definitive.
- **Bernoulli failure is LLM-level, not architecture-level**: all 3 arches fail in similar ways, so this is a tax we all pay until LLMs get better at small-sample CI reasoning.
- **The argument for 3-agent over 2-agent is robust** (separation of concerns, explicit error routing). The argument for 3-agent over 4-agent is *empirical* in this trial; with stronger models or Lean-heavy workloads, 4-agent could win.
- **Cost numbers assume Haiku 4.5 pricing**. With Opus 4.5 (~15× more expensive), all costs scale roughly 5-15× and the cost-of-extra-agents argument becomes much sharper.
