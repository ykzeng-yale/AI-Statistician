## Test questions (all backed by existing Mathlib lemmas)

### prob_measure_univ
- **English**: A probability measure assigns mass 1 to the universal set.
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `measure_univ`

### integral_of_constant
- **English**: The expected value of a constant c is c itself (for any probability measure).
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `simp [integral_const]`

### variance_of_constant
- **English**: The variance of a constant random variable is 0.
- **Mathlib namespace**: `ProbabilityTheory`
- **Expected lemma**: `simp [variance, evariance]`

### expectation_linearity
- **English**: The expected value of a sum equals the sum of expected values (for integrable variables).
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `integral_add hX hY`

### markov_inequality
- **English**: Markov's inequality: for measurable nonneg f and ε ≠ 0, ε ≠ ⊤, μ {x | ε ≤ f x} ≤ (∫⁻ x, f x ∂μ) / ε.
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `exact meas_ge_le_lintegral_div hf.aemeasurable hε hεt`

### variance_nonneg
- **English**: Variance is always non-negative.
- **Mathlib namespace**: `ProbabilityTheory`
- **Expected lemma**: `exact variance_nonneg X μ`

### variance_indep_add
- **English**: For independent L² random variables X, Y, Var[X + Y] = Var[X] + Var[Y].
- **Mathlib namespace**: `ProbabilityTheory`
- **Expected lemma**: `exact IndepFun.variance_add hX hY h_indep`

### integral_indicator_const
- **English**: Integral of a constant c times an indicator of a measurable set equals c times the measure of that set.
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `exact integral_indicator_const c hs`

### prob_compl
- **English**: For a probability measure μ and measurable event A, μ(Aᶜ) = 1 - μ(A).
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `exact prob_compl_eq_one_sub hA`

### norm_integral_le_integral_norm
- **English**: Triangle inequality for integrals: ‖∫ x, f x ∂μ‖ ≤ ∫ x, ‖f x‖ ∂μ.
- **Mathlib namespace**: `MeasureTheory`
- **Expected lemma**: `exact norm_integral_le_integral_norm f`

### What this means

Unlike the main `stat_research_agent.py` (which only generates Lean stmts with
`:= by sorry` and calls `axle.check`), this eval exercises **real proof
construction**: Claude proposes a proof term using existing Mathlib lemmas,
and AXLE's `verify_proof` either accepts it (proof is valid w.r.t. the kernel)
or rejects it (proof is malformed or wrong).

**This is the same loop AxiomProver uses on Putnam problems** —— compose
known Mathlib facts to prove a target. We've just specialized it to elementary
statistics.

### Where this fits in the pitch

- ✅ **Real formal verification capability**: Yes, we can actually prove things in Lean.
- ⚠️ **Scope**: Today we prove *known facts that Mathlib already has the lemma for*.
  This is the same scope AlphaProof / AxiomProver work at — composing existing facts.
- ❌ **Open frontier**: Proving *new* asymptotic stat theorems (CLT, MLE consistency)
  requires extending Mathlib first — that's the Axiom Math product roadmap.

### Failure mode analysis (the 6/10 cold fails)

Looking at the 6 cold failures, **all of them are premise-selection issues**:

| Question | Claude's wrong proof | Why it failed |
|---|---|---|
| `variance_of_constant` | `variance_const μ c` | Lemma doesn't exist by that name |
| `markov_inequality` | `meas_ge_le_lintegral_div hf hε hεt` | Needs `hf.aemeasurable`, not raw `hf` |
| `variance_indep_add` | `variance_add_of_indepFun hX hY h_indep` | Real name is `IndepFun.variance_add` (method syntax) |
| `integral_indicator_const` | (rambled, no proof emitted) | Couldn't identify the lemma at all |
| `prob_compl` | `rw [measure_compl hA, ...]` | Wrong rewrite chain |
| `norm_integral_le_integral_norm` | `norm_integral_le μ f` | Wrong name (`norm_integral_le_integral_norm f`) |

**Zero math-reasoning failures.** All 6 are *lemma-name lookup* failures. This
is a textbook case for premise selection / RAG.

## Related literature (from `chrome-paper-log/ai-math-discovery-systems/`)

The empirical finding above — that the cold→hinted gap is **entirely

on Lean RAG has identified. The field's solutions stratify into 3 layers:

### Premise selection / RAG over Mathlib (Layer 3 of the dependency spine)

| Approach | Paper / Tool | What it would solve in our failure cases |
|---|---|---|
| **Semantic / NL → lemma search** | [Lean Finder](https://arxiv.org/abs/2510.15940), [Semantic Search Engine for Mathlib4](https://arxiv.org/abs/2403.13310) | Map "variance is non-negative" → `variance_nonneg`; would close `variance_indep_add`, `prob_compl` |
| **Type/signature/subexpr search** | [Loogle](https://loogle.lean-lang.org/), [Moogle](https://www.moogle.ai/) | Search by goal shape `_ ≤ _ ∂μ` returns Markov-family lemmas; would close `markov_inequality`, `norm_integral_le_integral_norm` |
| **Retrieval-augmented theorem proving** | [LeanDojo + ReProver](https://arxiv.org/abs/2306.15626) | End-to-end retrieval+prover loop; production analog of our `formal_proof_eval.py` |
| **Mathlib dependency graph** | [The Network Structure of Mathlib](https://arxiv.org/abs/2604.24797), [MathlibGraph](https://huggingface.co/datasets/MathNetwork/MathlibGraph) | Index lemmas by their position in the proof DAG; useful when a target sits in a "hub" |

### Implications for the AI Statistician product

What we've measured (40% cold) is the **raw LLM ceiling** for elementary stats
Mathlib without retrieval. The literature suggests the realistic production
target stack — but a **mature engineering principle**: don't reinvent these
layers, *integrate* the proven open-source systems:

```
┌────────────────────────────────────────────────────────────────────────┐
│  Tier 1 (cheap, must-have):   INTEGRATE Loogle or Moogle API           │
│        Cost: ~10 LOC of HTTP client per lookup                         │
│        Source: https://loogle.lean-lang.org/json?q=...                 │
│        Expected lift: ~70% (off-the-shelf, no training)                │
├────────────────────────────────────────────────────────────────────────┤
│  Tier 2 (medium):             INTEGRATE Lean Finder (arXiv:2510.15940) │
│        Cost: install + serve their published model + cache embeddings  │

├────────────────────────────────────────────────────────────────────────┤
│  Tier 3 (heavy R&D):          FORK ReProver / DeepSeek-Prover & adapt  │
│        Cost: fine-tune their retrieval head on Mathlib's               │
│        MeasureTheory + ProbabilityTheory subset (~5–10k lemmas)        │
│        Expected lift: ~95% (matching Putnam-class baselines)           │
└────────────────────────────────────────────────────────────────────────┘
```

**Engineering principle (mention in interview)**:

> "We don't build our own RAG —— Loogle, Moogle, LeanDojo, and Lean Finder
> already solved this problem at the level we'd need for v1. Our value-add
> is *not* reinventing retrieval; it's (a) **specializing the index to
> statistics** (5–10k lemmas vs 300k = tractable for a small fine-tune),
> and (b) **closing the agentic loop** — orchestrating retrieval + LLM
> proposer + AXLE verifier + Monte Carlo simulator into a single product
> a statistician can actually use. The retrieval primitive is a commodity;
> the workflow is the differentiator."

### What "integrate" actually means in code

Tier 1 sketch (could be ~30 LOC in `formal_proof_eval.py`):

```python
# Integrate Loogle as the retrieval primitive — no new ML training required.
async def loogle_lookup(goal_shape: str) -> list[str]:
    """Hit the public Loogle HTTP API for lemmas matching a goal shape."""
    async with httpx.AsyncClient() as client:
        r = await client.get(
            "https://loogle.lean-lang.org/json",
            params={"q": goal_shape},
            timeout=10.0,
        )
        return [hit["name"] for hit in r.json().get("hits", [])[:10]]

# Then in FormalProofAgent._propose_proof, prepend retrieved lemma names
# to the prompt — without revealing the answer, just narrowing the search.
```

This is **not** in `formal_proof_eval.py` today by deliberate design — the
user's instruction was "don't build our own RAG; integrate". A future PR
would add `loogle_lookup()` and re-run the cold eval to confirm the 40 →
~70% lift the Loogle paper / docs predict.
